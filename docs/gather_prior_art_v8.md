# ASTC-KV: источники и гипотеза gather v8

Дата проверки публичных источников: 2026-10-29. Это независимый обзор перед интерпретацией нового опыта, без собственных GPU-измерений. Просмотрены отчеты v2/v3 и прежний scalar kernel. Старые exploratory captures не считаются новым набором для проверки качества. Файлы результатов не менялись.

## Почему проверяется gather

В `attention_atlas_v7.metal` один SIMD group обрабатывает одну query head и один context split. Для одного token/query-head четыре lanes читают по четыре группы из четырех scalar V texels: всего 64 вызова `tex.read`. При Hq9/Hkv3 это повторяется для трех query heads, использующих один KV head. Это подсчет вызовов в исходнике, а не измерение аппаратных инструкций, декомпрессий блока или обращений к DRAM: texture cache может переиспользовать данные.

Выбранная гипотеза: один `gather` возвращает четыре scalar значения из участка 2 tokens x 2 channels; дальнейшие веса и суммы вычисляет shader. При полном покрытии пар можно заменить четыре исходных texture-вызова одним. Формат, payload, ranges и порядок самих KV-значений сохраняются. GPU scheduling и порядок FP32-суммирования меняются, поэтому быстрый путь обязан отдельно пройти correctness.

Это более различающий опыт, чем еще одна перестановка адресной арифметики. Он проверяет цену получения соседних scalar значений. Однако один gather не обязан быть в четыре раза быстрее четырех reads и не гарантирует четырехкратного уменьшения трафика. Прежний ordinary-RGBA контроль уже показал, что сокращение количества вызовов само по себе не объясняет весь разрыв ASTC/FP16.

Зафиксированный координатором протокол находится в `configs/gather_v8_20261029.json`. Основной критерий: median ABBA/BAAB GPU ratio gather/hoisted <=0.85 при T8192 в каждом из пяти сеансов, при прежней persistent memory и пройденных correctness gates. Paired-direct является отдельным контролем изменения scheduling; сравнение с FP16 показывает оставшийся разрыв. Эти вторичные сравнения не заменяют основной критерий после результата. Этот документ не сообщает результат v8.

## Контракт точности

- Сравнить normalized gather output с прежним integer read побитно, независимо от attention. Проверить порядок компонентов gather, все KV heads, block/atlas seams и последний неполный участок.
- Для пары `t,t+1` и `c,c+1` четность должна относиться к абсолютным координатам. При четных t и c обе пары помещаются внутри 6x6 блока и соответствующего участка compact atlas. При odd split start локальные пары могут пересечь границу блока; нужен direct fallback. Проверки tile1/7/13 существенны.
- Маска второго token обязана действовать до чтения его metadata и использования значения. Нулевой вес не делает произвольное невалидное значение безопасным: `0*NaN` остается NaN.
- Attention сравнивается с независимым CPU FP64 reference представленных значений при прежнем пороге 1e-4. Численный порог не расширяется ради gather. Совпадение с codec reference не заменяет проверку исходного model quality.

## Проверенные первичные источники

Все ссылки ниже просмотрены 2026-10-29. Числа производительности сторонних работ здесь не воспроизводились.

1. [Sigg и Hadwiger, Fast Third-Order Texture Filtering, GPU Gems 2, 2005](https://developer.nvidia.com/gpugems/gpugems2/part-iii-high-quality-rendering/chapter-20-fast-third-order-texture-filtering). Авторы используют аппаратную линейную фильтрацию для вычисления взвешенных сумм соседних texels, уменьшая число fetches, и обсуждают ограничения точности. Поэтому перенос положительной пары `a*u0+b*u1` в линейный sample сам по себе не новый математический прием. Работа о фильтрации, не о KV attention.

2. [Akenine-Moller, Ebelin, Pharr, Wronski, Collaborative Texture Filtering, HPG 2025](https://research.nvidia.com/labs/rtr/publication/akeninemoller2025collaborative/). Авторы распределяют получение texels между lanes и переиспользуют декодированные значения через wave intrinsics. Устранение повторной декомпрессии и совместное чтение соседями уже известны. Эта работа не устанавливает результат для ASTC-KV attention.

3. [FlashInfer, arXiv:2501.01005v2, 2025-04-21, Appendix A](https://arxiv.org/html/2501.01005v2). Head-group fusion объединяет query heads с общей KV head, чтобы переиспользовать одну загрузку KV. Поэтому совместное GQA-исполнение является известной оптимизацией. Возможный вклад нашей реализации потребовал бы отдельного выигрыша ASTC после применения сопоставимой оптимизации к FP16.

Дополнительные источники для альтернатив и границ вклада:

- [Apple, Boost your graphics performance with the M5 and A19 GPUs](https://developer.apple.com/videos/play/tech-talks/111431/). Дата публикации в просмотренной странице явно не указана. Apple описывает lossless universal texture compression на M5, поддержку compute shader writes, заполнение через GPU blit, риски scattered updates и счетчики texture decompression stalls/compression ratio. Это не ASTC-кодировщик и не обещание уменьшить `allocatedSize`.
- [Compute ASTC, авторский материал от 2021-12-18](https://niepp.github.io/2021/12/18/Compute-ASTC.html) и [авторский код](https://github.com/niepp/astc_encoder). Уже существует runtime compute encoding ограниченного ASTC: без поиска partitions, с 4x4 weight grid, ограниченными modes. Репозиторий описывает D3D11; это не проверенный готовый Metal KV encoder.
- [Apple AFM, arXiv:2507.13575v3, 2025-08-27, раздел 6](https://arxiv.org/html/2507.13575v3). Применяет ASTC HDR-ch к весам, minimum shift и fused восстановление. Hardware decoding нейротензоров известно. Качество адаптированных весов не переносится автоматически на динамический KV.
- [ZipFusion, arXiv:2610.33719v1, 2026-10-24](https://arxiv.org/abs/2610.33719v1). Публичная статья описывает lossless KV, реконструкцию в registers внутри attention, FlashInfer/SGLang и NVIDIA H100. Это дополнительный прямой аналог активного сжатого KV без отдельного полного восстановления. Приведенные авторами ускорения не проверялись локально.

Ограниченный публичный поиск не выявил точного примера `ASTC scalar KV + exact 2x2 gather + paired attention`. Это отсутствие найденной ссылки, а не доказательство мирового приоритета. Общие идеи gather, совместного чтения, аппаратной фильтрации, compressed attention и head fusion уже известны. Потенциальный результат здесь - проверенный полезный способ исполнения конкретного представления.

## Три альтернативы после основного опыта

Порядок отражает ожидаемую различающую способность и стоимость проверки, а не установленный выигрыш. Пороги ниже являются предложениями для отдельных будущих регистраций; они не меняют критерий v8.

1. **Совместное GQA.** Обрабатывать три Q-heads общей KV-head совместно, сохраняя независимые scores, softmax states и outputs. Гипотеза: одна загрузка/декомпрессия V на три потребителя компенсирует texture cost. Малый опыт: D64/Hq9/Hkv3, T384 и T8192, один фиксированный tile, четыре варианта - старый и fused ASTC, старый и fused FP16. Контроль GQA-group1 отделяет накладные расходы объединения. Продолжать ASTC-ветку только при выигрыше относительно столь же fused FP16; ускорение обеих веток без изменения разрыва не подтверждает ASTC-specific преимущество. Риск: дополнительные Q/accumulators увеличат register pressure. Новизна head fusion отсутствует, переносимость выигрыша неизвестна.

2. **M5 lossless texture и дешевый append.** Гипотеза: ordinary texture с автоматическим lossless compression дает достаточную экономию трафика без сложного ASTC encoder. Прежний `ordinaryTexture` уже использует private texture и GPU blit, поэтому такая компрессия могла действовать в старых контролях. Отличающий опыт: одинаковые R16/RGBA16 данные и kernel при `allowGPUOptimizedContents` true/false, затем отдельно один compute append в заранее выделенную texture. Проверять точный readback, GPU-time и доступные compression counters. Выигрыш должен сохраняться при включенной стоимости append; равный `allocatedSize` не опровергает экономию bandwidth и не доказывает экономию capacity. Новизна аппаратного механизма отсутствует; эффективность для KV неизвестна.

3. **Положительная weighted pair через linear sample.** При `a=w0*s0`, `b=w1*s1`, `a,b>=0`, можно вычислить `(a+b)*lerp(u0,u1,b/(a+b))`, а offset contribution прибавить отдельно. Нужна явная ветка `a+b==0`. В отличие от gather, этот путь вводит ошибку аппаратной интерполяции. Самый дешевый различающий опыт - texture с известными парами значений, dense sweep коэффициента f от 0 до 1 и сравнение с FP32 arithmetic, включая zero scale, почти единичный/нулевой вес и cancellation после offsets. Если прежний numerical gate не проходит, не переходить к model timing и не расширять допуск. Формула известна как минимум с GPU Gems 2; возможная польза ASTC-KV остается гипотезой.

BC4/BC5 также заслуживают ограниченного codec-control, но не нового широкого sweep. [Таблица возможностей Apple от 2026-05-21](https://developer.apple.com/metal/Metal-Feature-Set-Tables.pdf) перечисляет BC formats начиная с Apple9. BC5 имеет два отдельно кодируемых scalar канала и поэтому отличается от уже неудачного naive RGBA ASTC с общими цветовыми ограничениями. Поддержку конкретного формата, качество, реальный allocation и цену reads нужно проверять, а не выводить из названия формата. Пока это запасная альтернатива, не выбранный v8-кандидат.

## Почему пока не начинать большой GPU encoder

Compute ASTC доказывает принципиальную осуществимость ограниченного GPU encoding, но не нужное качество или цену маленького KV append. В старом H1a identity encoder выбрал несколько partitions для 27812 из 38016 блоков. Это не доказательство необходимости этих partitions, но явный риск переноса однопартиционного быстрого кодировщика.

До полноценного Metal encoder достаточно отдельного CPU-control с `tune_partition_count_limit=1` на прежних captures при тех же ranges и учете всех bits. Это оптимистичный контроль только ограничения partitions, а не эквивалент Compute ASTC с его 4x4 weight grid. Если качество уже существенно хуже принятого baseline, перенос этого семейства encoder на GPU следует остановить. Если контроль пройдет, еще нужны encoding cost, GPU buffer-to-texture blit, completion/publication страницы и causal append. Encoder не устраняет уже измеренный проигрыш самого чтения; сначала требуется полезный precompressed путь.
